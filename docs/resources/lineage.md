# Instance lineage (concept only)

Status: package `lineage/`, not used by any page yet (Nina 2026-11-09: implement as a concept, no module integration).
Concept: `overview/concepts/Transformations.md`, sections "Instance Lineage" and "Instance Visualisation" (outside this repo).
Demo: `notebooks/lineage.ipynb`.

## What it shows
For a selected handling unit, which handling units it was made from (components) and what it was turned into (products), over a chosen number of generations, as a graph:
- **Object graph**: one node per handling unit (filled in the colour of its object type), arcs component → product labelled with the transformation event.
- **Bipartite graph**: handling units and transformation events (white boxes with event id and activity), arcs component → event → product.
- **Siblings** (optional): the handling units produced together with a lineage hu but not part of the lineage, greyed and dashed; in the object graph joined to that hu by an undirected dashed edge, in the bipartite graph by an arc from their shared creation event.
- The selected handling unit has a thick black border.

## How it is calculated
Concept definitions (Transformations note):
- Lineage relations $R = \{(hu, hu', e) \mid e \in T: hu \in cons(e), hu' \in prod(e)\}$: `lineage_relations`, a join of the consumed and the produced handling units on the event.
- $parents$, $children$, $ev_{prod}$ (creation event), $E_{cons}$ (consumption events), $siblings$ (co-produced hus): `parents`, `children`, `creation_events`, `consumption_events`, `siblings`, each as a relation table.
- Lineage $R(hu, dir, gen)$: generation by generation, one filter per generation on the previous generation's frontier (`generations`), until `gen` generations or an empty generation; a relation reached again in a later generation (diamond-shaped lineage) keeps its first generation.
- Graphs: `lineage_graph` builds the nodes $O'$, $T'$, $S$ and the edges of the note's box "Lineage graphs"; `to_dot` writes Graphviz DOT source.

Inputs: the transformation roles ($cons$, $prod$) as one table with the columns `event`, `hu`, `role` (`consumed`/`produced`), e.g. `data/running_example/inputs/transformation_roles.csv`.
How $cons$ and $prod$ are derived from user inputs (options 1 to 6 of the note) is not implemented yet.

## Example
Running example: $R = \{(s1, c1, e3), (s1, c2, e3), (c2, c4, e15)\}$.

| function | result |
|---|---|
| parents | c1: s1, c2: s1, c4: c2 |
| children | s1: c1, c2; c2: c4 |
| creation events | s1: e1, c1: e3, c2: e3, c4: e15 |
| consumption events | s1: e3, c2: e15 |
| siblings | c1: c2, c2: c1 |
| R(c2, both, ∞) | (s1, c2, e3), (c2, c4, e15) |
| R(c4, components, ∞) | (c2, c4, e15) gen. 1, (s1, c2, e3) gen. 2 |

Graphs of c2 (both, all generations): $O' = \{s1, c2, c4\}$, $T' = \{e3, e15\}$, $S = \{c1\}$; figures in the Transformations note (generated by `claude_notes/figures/lineage/make_lineage_figures.py`, outside this repo).
Tests: `backend-modules/location-ocpm/tests/test_lineage.py` (also a diamond-shaped example).

## Settings
| parameter | meaning | default |
|---|---|---|
| `hu` | selected handling unit | |
| `direction` | `components`, `products` or `both` | `both` |
| `gen` | generations per direction, a natural number or `math.inf` | `math.inf` |
| `with_events` | bipartite graph instead of object graph | `False` |
| `with_siblings` | add siblings | `False` |
| `object_types`, `activities` (`to_dot`) | labels and colours | none |

## Where it lives in the code
`backend-modules/location-ocpm/src/ocelescope_module_location_based_ocpm/lineage/`:
- `relations.py`: `roles_of`, `lineage_relations`, `creation_events`, `consumption_events`, `parents`, `children`, `siblings`.
- `lineage.py`: `generations(relations, hu, direction, gen)`, `lineage(relations, hu, direction="both", gen=inf)`.
- `graph.py`: `lineage_graph(...) -> LineageGraph(nodes, edges)`, `to_dot(graph, object_types, activities, rankdir="LR")`, `type_colours`.

## How to change it
- Other sibling notion (e.g. all hus sharing a parent): change `relations.siblings`; `graph.lineage_graph` and the tests use it.
- Other styling: `graph.to_dot` (colours from the module palette `visits/trace_figure.CATEGORICAL`).
- Large logs: `generations` filters R once per generation; for many lineages at once, index R by parent and child first.

## Alternatives
- Rendering with ELK or the Ocelescope graph viewer instead of Graphviz: left for the page integration; `lineage_graph` returns plain tables so any renderer can be used.
- Siblings as all hus sharing a parent: rejected (Nina 2026-11-09), siblings are co-produced.
