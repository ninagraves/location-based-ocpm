# Directly-follows graph page

Status: **suggestion** (2026-11-14), built from Nina's brief in the project thread "Build directly-follows graph page"; to be reviewed by Nina before it counts as conceptualised.
User-facing description: module note `overview/module/Directly-Follows Graph Page.md` (outside this repo).
The page will be extended (more interaction) later; the code is split into one step per module so that steps can be replaced one at a time.

## Brief (Nina, 2026-11-14)
- Replaces Ocelescope's default DFG module. Disliked there: the layout (all start nodes on the same height at the top), the two places for settings (discovery form and viewer), activity names that are cut off, too large frequency labels on the arcs.
- All settings in a sidebar of the page.
- Only the directly-follows relations of the handling units are shown by default; other object types involved appear only as circles on the activity nodes (as in TOTeM's discovery view, https://totem-tool.com/#discovery), unless they are selected.
- Arc and path filter thresholds per object type.
- Round 6 (Nina, 2026-11-15): "paths" renamed "variants"; activity selection as in Ocelescope (projection before everything else), per object type, default 40 % of a type's activities (3 to 10); arc threshold as Ocelescope's DFG filter, default 100 %; optional "Stay connected" (default on); an arc count slider like Ocelescope's DFG viewer; default variant threshold: one value for all types keeping at least the top 3 variants of each; arcs removable by right click.
- Object types named in the model; activity frequencies in the nodes.
- Round 8 (Nina, 2026-11-16): Arcs (display) moves to the toolbar (between direction and Compact) with a General / Per type toggle (default General) and − / + buttons; direction as arrows; a settings button next to Reset shows or hides the sidebar, now titled "Discovery Settings", which reaches from the top of the toolbar to the bottom of the graph; the sidebar no longer shows numbers of variants or arcs; activities not in the graph show the Arcs (projection) (upper part) or variant threshold (lower part) they would need instead of "deselected"; activity search also by category words, with "Select all"; defaults Arcs (projection) 50 %, Variants 80 %, Move to vehicle and Move to storage deselected.
- Layout and look of Ocelescope's earlier graph view of DFGs (ELK, `DirectlyFollowsGraph._visualize_graph` in `ocelescope/resource/default/dfg.py`), with smaller arc labels and complete activity names.

## Page structure
Configuration bar (shared header, `configuration.md`), then two columns: on the left the **toolbar** (event categories; arc labels, direction (→ / ↓), Arcs (display), compact, reset, settings button; `components/DfgToolbar.tsx`, Nina, 2026-11-15/16), the **legend** in grey and the **graph** (760 px high by default, pan and zoom with the mouse; buttons zoom in, zoom out, fit; nodes can be dragged and their arcs follow; the grab bar below the graph changes its height, 300–4000 px, double click: back to 760 px; kept per browser tab, key `dfg.height`), and the sidebar **Discovery Settings** (right, from the top of the toolbar to the bottom of the graph, scrolls inside; Nina, 2026-11-14/16). The object type list scrolls from `TYPE_LIST_HEIGHT` (160 px, about 6 types); the activity list takes the rest of the sidebar's height, at least `ACTIVITY_LIST_MIN_HEIGHT` (360 px) (Nina, 2026-11-19; before 300 and 320 px). The sidebar is 300 px wide by default; dragging its left edge changes the width (220–640 px; a thin line appears on hover); the settings button (sliders icon, right of Reset) hides and shows it (shown by default). Width and visibility are kept for the browser tab (`usePageState`, key `dfg.sidebar`, the same for all logs).
The view is fitted to the graph when it changes, but never enlarged beyond 100 %, so a small graph is not blown up.
The page ignores the overview page's filter bar and has no filters beyond its own settings (Nina, 2026-11-14: not for now). It uses the configuration for the handling units HU, the movement events M and the processing operations P (tie order); it does not use locations yet.

## 1. What the graph shows
For a log with object types $OT$, the user selects $OT_{sel} \subseteq OT$ (default: the object types that contain handling units).
**Considered objects** $O_{ot}$ of a selected type $ot$: its handling units if $ot$ contains handling units (with HU given as object types: all objects of $ot$; with a HU table: only the listed objects of $ot$), otherwise all objects of $ot$.
**Trace** of an object: its events (e2o, an object linked twice to an event counts once) ordered by time, then the **DFG boundary rank** (`dfg/traces.py`, `boundary_rank`; Nina, 2026-11-14): among events at the object's first timestamp a transformation event comes first (it creates the object), among events at its last timestamp a transformation event comes last (it consumes the object); if all its events share one timestamp, the first rule applies. Then the AS4 tie rank (movements, processing operations, rest; `visits/order.py`), then event id. Apart from the boundary rank this is the `seq` order of otrace(hu) on the other pages.

| Element | Shows | Calculated by |
|---|---|---|
| Activity node | full activity name (12 px, regular, **bold only in the compact layout**; wrapped at 150 px, never cut), below it one row with its **frequency** (events of the activity in the included traces) followed by one small circle per **unselected** object type involved in these events (same row, so nodes stay flat; Nina, 2026-11-14) | `dfg/nodes.py` |
| Start node ▶ / end node ■ | one per selected type with a kept start / end arc; filled with the type's colour, the type's **name** below; arcs from start nodes and to end nodes are **grey** (Nina, 2026-11-14) | `dfg/arcs.py` (null source / target) |
| Arc | directly-follows arc $(a, b)$ between two activities of a selected type in its colour; thickness 1.2–4 px by $\sqrt{count / \max count}$ of the type; small label (10 px) with the traversals or the objects, plain text sitting on the arc (the arc runs through it, as in Ocelescope's earlier view) | `dfg/arcs.py` |
| Hover activity | name, events shown (and in the log if different), per involved type: events and objects | `components/DfgGraph.tsx`, `activityTooltip` |
| Hover circle | "truck: 2 of 2 events, 1 objects" | `DfgGraph.tsx`, `ActivityNode` |
| Hover arc label | traversals and objects of the arc | `DfgGraph.tsx`, `ArcEdge` |

Definitions (`dfg/arcs.py`): for an object $o$ of type $ot$ with trace $\langle e_1, \dots, e_n \rangle$, the arcs are $(\triangleright_{ot}, act(e_1))$, $(act(e_i), act(e_{i+1}))$ and $(act(e_n), \square_{ot})$. $count(arc)$ = traversals (an object repeating an arc counts once per traversal), $objects(arc)$ = distinct objects.
**Order of the steps** (Nina, 2026-11-15): 1. traces, 2. **projection**: removing the events of deselected **event categories**, then of deselected activities, 3. **variant filter**, 4. arcs, **arc threshold**, **arc count**, **arcs removed by hand**, 5. **Stay connected** (optional), 6. nodes.
**Where they run** (Nina, 2026-11-15, for speed): steps 1–3, the arcs of the included traces and the nodes in the backend (route); the arc settings of steps 4–5 in the browser (`lib/dfgArcs.ts`, `lib/dfgView.ts`), so the arc sliders, Stay connected and the right click react without a request. The Python functions of steps 4–5 (`dfg/arcs.py`, `dfg/connectivity.py`) stay for the notebook, the tests and analyses outside the page; `tests/test_dfg_frontend.py` runs the TypeScript version with Node and checks that both give the same arcs (Nina chose to keep both).
**Included traces**: the projected traces of the objects whose variant is kept by the variant filter. They are the baseline of everything after the variant filter: arcs, frequencies and involved types only use events on included traces.
Shown activities: every activity that is the source or target of a shown arc. Frequency of activity $a$: $|\{e \mid act(e) = a,\ e$ on an included trace$\}|$.
Involved types of $a$: for every object type (selected or not), the frequency events of $a$ that involve at least one object of that type, and its distinct objects there.

**Event categories** (`dfg/categories.py`, `event_categories`, `remove_categories`; Nina, 2026-11-15): Movements = $M$; Move to vehicle = movements with target location $uloc(e) \in V$; Move to storage = movements with $uloc(e) \in W$; Processing = $P$; Transforming = $T$. Deselecting one removes its events from the traces of every type before the activity projection (a projection: $\langle a, b, c \rangle$ without $b$ becomes $\langle a, c \rangle$). The categories overlap: an event is removed only when **all** categories it belongs to are deselected (Nina, 2026-11-15). Events in no category are not affected by the chips; the activity selection still applies to them. A category without events (e.g. no vehicles configured) is disabled. Example (running example with $V$ = {T}, $W$ = {B1}): deselecting only Move to vehicle removes nothing (the two "load truck" events are also movements); deselecting only Movements removes the 4 movements to A2 and keeps the 2 to T and the 2 to B1; deselecting all three removes all 8 movements.
**Category badges** (Nina, 2026-11-15): every activity in the list carries a small single-letter badge per category of its events (Nina: small, unobtrusive): M movements, V to a vehicle, W to a storage unit, P processing, T transformations, counted among its events with a handling unit (the number in brackets); a letter is underlined (dotted) if only some of the events are in the category; hovering shows the counts (e.g. "W: 1 of 4 events are movements to a storage unit"). The unfold shows the same per object type, among the events with a considered object of the type (`_category_badges`, `categories.grouped_category_counts`, computed once per log in `log_frames`).
**Activity list in two parts** (Nina, 2026-11-17; before: upper part = on an included trace): the upper part lists the activities **in the graph** (`graph.activities` after the arc settings), the lower part ("Not in the graph") the others. Lower part, first (blue numbers, `PROJECTION_COLOUR`): activities on an included trace without a drawn arc, with the Arcs (projection) they need (see below), least first; then (grey numbers): activities on no included trace, each with the smallest whole variant threshold that would put it on an included trace (`variant_threshold_needed`, "≥ 21 %": the minimum over the selected types; least first); for a deselected activity, the threshold it would need if it were selected as well (`variants.added_activity_thresholds`: the traces projected on the selected activities plus this one; Nina, 2026-11-16, instead of the label "deselected"). Unfolded, every selected type shows its own value **with up to 3 decimals** (`variant_threshold_needed_exact`, `variants.EXACT_DECIMALS`: the share before rounded down to 3 decimals plus 0.001, e.g. 2 of 3 objects before → "≥ 66.667 %" where the summary says "≥ 67 %"; Nina, 2026-11-18), "in the graph", or why no threshold helps: "removed by an event category" or "type not selected" (`variants.activity_variant_thresholds`: for an activity, the variants containing it after the projection, ranked as for the variant filter; the needed threshold is $\min(100, \lfloor 100 \cdot covered\_before / |O_{ot}| \rfloor + 1)$ of its best-ranked variant). Example (worked example of the module note, pallets, all activities): inspect needs 51 % (its first variant has 5 of 10 pallets before it; unfolded 50.001 %), scrap 81 % (80.001 %); the same with inspect and scrap deselected. "event category" (summary) / "removed by an event category" (unfold) is shown for checked **and unchecked** activities whose events of the type were all removed by the event category chips: no variant threshold helps either way (Nina, 2026-11-18; before, unchecked ones showed nothing).
**Upper part, unfolded** (Nina, 2026-11-19): an activity in the graph can lack a drawn arc for some selected types (e.g. because of Arcs (projection)). For these types the unfold shows the same values as the lower part: blue Arcs (projection) needed (or "display") if the activity is on an included trace of the type, else the grey variant threshold (or the reason none helps); types with a drawn arc show nothing (`missingTypes`, `projectionNeeds(option, types)` in `DfgSettings.tsx`).
**Third part "Without handling units"** (Nina, 2026-11-19): activities not in the graph with no event that involves a handling unit (`hu_events` 0), easiest first. Instead of the variant threshold, the summary names the object type for which the activity is easiest to include, e.g. "operator · ≥ 67 %" (`DfgActivityOption.easiest_type`: the type with the smallest `variant_threshold_needed_exact`; ties: selected types first, then most events, then name). For these activities every type gets a value, also an unselected one: the threshold it would need if the type were selected with its default activities (`graph.unselected_type_thresholds`: traces of the unselected types after the event categories, projected on `default_activities` (with the shared handling-unit defaults); `activity_variant_thresholds` if the activity is a default, else `added_activity_thresholds`). Blue values (Arcs (projection)) as in the lower part. The unfold shows every type, selected or not. Example (`test_activities_without_handling_units_name_the_easiest_type`): operators o2 (tea, train), o3 (train, handover), o1 (inspect, …, break), one object each, ranked in this order; break → operator, 66.667 %; handover: truck 50.001 %, operator 33.334 % → operator. Computed only if the log has such activities; it builds the traces of every unselected type with such an activity (cost grows with these types' objects).
**Arcs (projection) needed** (Nina, 2026-11-16/17; blue, hover: "For the Arcs (projection) slider"): an activity on an included trace but without a drawn arc shows the smallest Arcs (projection) at which one of its arcs is kept, "≥ 60 %" (the minimum over the selected types; per type in the unfold with up to 3 decimals, `neededArcThresholds(arcs, 3)`, e.g. 7 of 17 arcs ranked before → 41.177 %; `lib/dfgArcs.ts`, `neededArcThresholds`: $\min(100, \lfloor 100 (r - 1)/n \rfloor + 1)$ for its best arc, $r$ = its rank with ties (the first rank of its tie group), $n$ = arcs of the type), or "display" if Arcs (projection) already keeps one of its arcs and Arcs (display) or a hand removal hides it.

**Activity selection (projection)** (`dfg/projection.py`; Nina, 2026-11-15): as in Ocelescope's DFG discovery (`ocelescope.discovery.algorithms.dfg_miner`, which removes excluded activities before the directly-follows relations). For every selected type the events of its deselected activities are removed from its traces right after the event categories, before anything else: a trace $\langle a, b, c \rangle$ with $b$ deselected becomes $\langle a, c \rangle$, so variants, arcs and frequencies are computed on the projected traces. An object whose projected trace is empty is left out.
The list shows per activity its events with at least one handling unit (`handling_unit_event_counts`); its checkbox (de)selects it for every selected type with events of it (indeterminate if selected for some of them). The unfold lists every object type with events of the activity (`type_activity_counts`: events with at least one considered object of the type); only selected types can be (de)selected. Default per type (`default_activities`, `default_activity_count`): the $\min(n, \max(3, \min(10, \lceil 0.4\,n \rceil)))$ most frequent of its $n$ activities (by events of its considered objects; ties by first occurrence, then name). E.g. $n$ = 7 → 3, 12 → 5, 30 → 10. **Shared** (Nina, 2026-11-16): every activity preselected for one selected handling-unit type is preselected for every selected type that has events of it (`default_activities(counts, object_types, shared_from)`, `shared_from` = the selected handling-unit types), so a type may get more than 10. E.g. running example: coil's own 3 (crane move, quality check, load truck) plus roll from slab's default (cast slab, inspect slab, roll), as coils take part in roll. Once the user changes a type, its full list is stored (`DfgState.activities`), so it no longer follows the default; "Default" in the list header clears all.

**Variant threshold** $\pi_{ot}$ (`dfg/variants.py`): the variant of an object is the sequence of the activities of its projected trace. Variants of $ot$ are ranked by their number of objects (descending; ties by first occurrence in the log, then alphabetically), and a variant is kept if the objects of the variants ranked before it cover less than $\pi_{ot}/100 \cdot |O_{ot}|$. 0 % keeps none; ties are deliberately not kept together.
**Default**: 80 % for every type (`DEFAULT_VARIANT_THRESHOLD`, Nina 2026-11-16). E.g. running example: 5 coils with a variant each → 4 variants (4 coils); the slab's only variant.

**Arcs (projection)**, the arc threshold $\alpha_{ot}$ (Nina, 2026-11-16: "projection" vs "display" for the two arc sliders; `arcs.arc_share_filter`, as `DirectlyFollowsGraph.filter_edges` of Ocelescope without its repair): all $n$ arcs of $ot$, **start and end arcs included**, are ranked by objects, then traversals; the first $\lceil \alpha_{ot}/100 \cdot n \rceil$ are kept, plus every arc tied with the last kept one. 0 % keeps none.
**Arcs (display)**, the arc count $N_{ot}$ (`arcs.arc_count_filter`, like the slider of Ocelescope's DFG viewer `OCDFGViewer` in `@r4pm/components`): of the arcs left by the arc threshold, the first $N_{ot}$ in the order objects, traversals (descending), first occurrence (time of the first traversal), source, target; exactly $N_{ot}$ (ties broken by this order; Nina, 2026-11-15). **General mode** (default; Nina, 2026-11-16): the types without an own count share one limit $N$: their arcs are pooled and ranked by objects, traversals (descending), their position in their type's order, then object type; the first $N$ are shown. E.g. coil 6 and slab 4 arcs left, $N$ = 5: the 5 arcs with the most objects of both types together.
**Arcs removed by hand** (`arcs.remove_arcs`): removed after the arc count. **Without a new layout** (Nina, 2026-11-17): a right click applies at once, without the 2 s wait, if no other change is waiting. If the new graph only lacks arcs (`dfgLayout.reduceLayout`), the current layout is kept: the arc disappears, an activity left without arcs disappears and leaves a gap, nothing moves, dragged nodes stay where they were, and the view is not refitted. If Stay connected has to add an arc that was not drawn, the graph is laid out again (`DfgGraph`, `keepLayout`; the route sets it when the applied states differ only by more removed arcs, `onlyRemovedDiffers`). **Right click on an activity** copies its name to the clipboard ("Copied …" shows briefly; `onNodeContextMenu`).
**Activity nodes**: a right click copies the activity's name (Nina, 2026-11-17); a **double click deselects the activity for every selected object type** (`deselectActivity` in `routes/DirectlyFollowsGraph.tsx`, `onNodeDoubleClick` in `DfgGraph.tsx`; Nina, 2026-11-19), applied after the usual 2 s wait like a checkbox in the sidebar. Zoom on double click is switched off, so that the double click does only this. Example: coil selects crane move, roll, cut and slab cast slab, roll; a double click on roll leaves crane move, cut and cast slab.
**Stay connected** (`dfg/connectivity.py`, `stay_connected`; as the repair in Ocelescope's `filter_edges`): per type, base graph = the arcs of the included traces without the arcs removed by hand, reduced to the arcs on a start-to-end path (`on_start_end_paths`); required activities = the endpoints of the arcs left after the hand removals; every other base arc is then taken out, least frequent first, unless this cuts a required activity off from the start or the end node. It overrides the arc threshold and the arc count, nothing else: it never adds arcs of removed variants, of deselected activities or removed by hand (Nina, 2026-11-15). Added arcs have `connecting` = true; they are drawn like all other arcs, and hovering the line or its label says that they are only kept to stay connected (Nina, 2026-11-17; drawn dashed before).
All percentage comparisons are done in whole numbers times 100 (rounded to 6 decimals), so e.g. 60 % of 5 objects is exactly 3.

**Independence of settings**: changing one setting leaves all others as they are. Settings are kept per log across page switches and reloads (`lib/pageState.ts`, key `dfg.v5.<log id>`; settings saved by an older version are completed with the defaults). A slider sends its value when released. **Delayed recalculation** (Nina, 2026-11-17): the graph follows the settings only 2 s after the last change (`lib/useDebounced.ts`, `RECALCULATION_DELAY_MS` in `routes/DirectlyFollowsGraph.tsx`), so several settings can be changed first and only one request is sent; the controls show the new values at once (the sidebar's checkboxes via `dfgView.pendingSelection`), and **Update now** (toolbar, shown while a change waits) recalculates at once. This covers every setting that changes the drawing, including arc labels, direction, Compact and arcs removed by hand.

**Example** (running example, Level 3, default selection coil and slab): defaults: Movements, Move to vehicle and Move to storage deselected, so the events of crane move, load truck and unload truck are removed; coil has 4 activities with events left (quality check, roll, cut, label), so its own defaults are quality check, roll, label (3 of 4; label before cut by first occurrence), roll also shared from slab; slab: cast slab, inspect slab, roll (3 of 3); Arcs (display) all: "8 of 8 arcs + 1 to stay connected". Graph: cast slab, inspect slab, label, quality check, roll. The lower list shows crane move, load truck and unload truck (unchecked) with "event category" and cut with "≥ 1 %" (`test_default_activities_skip_activities_without_events_left`).
coil with all activities, Variants 100 %, Arcs 20 %: 18 arcs, $\lceil 3.6 \rceil = 4$, the fourth (2 objects) is tied with four more → 8 arcs. Arc count 2 instead: quality check → ■ (4) and load truck → unload truck (3). slab with Arc count 1: ▶ → cast slab, and Stay connected adds the other three.

**Save to session** (bottom of the sidebar, below the scrolling part; `components/DfgSave.tsx`, route `POST /{ocel_id}/dfg/save` (`saveDirectlyFollowsGraph`, body `DfgSaveRequest`), `dfg/export.py`; Nina, 2026-11-16/19): two selections and a name, then *Save*. It saves what was last drawn (the button waits while a change is pending).
- **Model**: Ocelescope's `DirectlyFollowsGraph` resource (`ocelescope.resource.default.dfg`; `export.dfg_resource`: one edge per arc with `count` = traversals, `object_count` = objects; start / end = None), added with `session.add_resource`. **Projected**: the arcs with the page's arc settings but Arcs (display) at all and no arcs removed by hand (Stay connected as set; `arcsToSave` in the browser, so it is exactly what the page would draw); **Displayed**: the arcs as drawn.
- **Log**: a new OCEL, added with `session.add_ocel` (it appears in the list of logs). The backend recomputes the included traces from the request (`graph.included_traces`, steps 1–3, the same function the graph uses) and keeps their events (`export.kept_event_ids`); `export.filtered_log` cuts them out of the log with Ocelescope's filter engine (`EventIdFilter`: the ids go through a temporary Parquet file, so a large selection stays one join), which drops relations to other events and objects left in no relation. Events keep all their relations, so objects of other types (and objects of a selected type on a removed variant that share a kept event) stay. **Projected**: all events of the included traces; **Displayed**: only those of the drawn activities (arcs hidden between two drawn activities cannot be taken out of a log).
- Example (running example, defaults): Log + Projected keeps 7 events (e1, e2, e3, e4, e7, e14, e16) of 17; Model + Displayed has the 9 drawn arcs (`tests/test_dfg_export.py`).

## 3. Layout
ELK layered (`lib/dfgLayout.ts`, `layoutGraph`, options `ELK_OPTIONS`; with "Compact layout" `COMPACT_OPTIONS`): the options of Ocelescope's `DIRECTED_ELK_GRAPH_LAYOUT` (network-simplex layering and node placement, layer-sweep crossing minimisation, spline edges), with somewhat smaller spacing between layers.
- Start and end nodes get **no** layer constraint: network-simplex layering places them right before their first (after their last) activity instead of all at the top.
- Activity nodes are tight around their text (`SIZES`: name 12 px, frequency 10 px, padding 2 × 5 px) and sized from the rendered text (`textWidth` measures with an invisible span in the page), so names are never cut; names wrap at spaces beyond 150 px (`wrapName`).
- Arc labels are ELK edge labels (centre placement, `elk.edgeLabels.inline`: the arc is routed through its label), so ELK reserves room for them; the object-type name below start and end nodes is an outside node label (`OUTSIDE V_BOTTOM H_CENTER`).
- Arrowheads have a fixed size (about 8 px), independent of the arc's thickness.
- Colours: `emphasisColourMap` (`lib/palette.ts`): handling-unit types get the signature colours `SIGNATURE` (petrol, pink, turquoise, blue, orange) first, all other types further categorical colours with opacity `FADED_ALPHA` (0.55), each group in the order of all object types (most objects first), so a type keeps its colour (Nina, 2026-11-15).
- Rendering: React Flow (`@xyflow/react`). Nodes can be dragged (Nina, 2026-11-15); an arc of a dragged node keeps ELK's route, bent so that its first point moves with the source node, its last with the target node and the points in between proportionally (`bendPath`, `followNodes` in `DfgGraph.tsx`; a self-loop is simply shifted); its label moves by the mean of both offsets. Positions return to the layout whenever a setting changes the layout. The edge paths come from ELK (`sectionPath`; spline bend points are cubic Bézier control points).

## 5. How to change
- Default activities: `DEFAULT_ACTIVITY_SHARE`, `MIN_ACTIVITIES`, `MAX_ACTIVITIES` in `dfg/projection.py`.
- Number of variants of the default threshold: `TOP_VARIANTS` in `dfg/variants.py`.
- Other defaults: `DEFAULT_ARC_THRESHOLD` / `DEFAULT_VARIANT_THRESHOLD` / `DEFAULT_STAY_CONNECTED` in `dfg/graph.py` and `DEFAULT_EXCLUDED` in `dfg/categories.py`, **and** `DEFAULT_STATE` in `DfgSettings.tsx` (arc count mode, categories). Back to the computed variant default (top 3 variants of every type): use `default_variant_threshold` for `variant_default` in `directly_follows_graph`.
- Waiting time before the graph is recalculated: `RECALCULATION_DELAY_MS` in `routes/DirectlyFollowsGraph.tsx` (0 = at once).
- Search words of the activity list: `CATEGORY_WORDS` in `DfgSettings.tsx`.
- Other tie order of traces: `visits/order.py`, `tie_rank` (changes all pages).
- Other variant filter: `variants.kept_variants`; other arc ranking: `arcs.arc_order` (arc count, sent as `rank`) and the key in `arcs.arc_share_filter` (arc threshold). Any change to steps 4–5 must be made in **both** `dfg/arcs.py` / `dfg/connectivity.py` and `lib/dfgArcs.ts`; `test_dfg_frontend.py` fails otherwise.
- Other event categories: `CATEGORIES` and `event_categories` in `dfg/categories.py` (the toolbar shows whatever the backend sends; badge letters `CATEGORY_BADGE` in `DfgSettings.tsx`). Removing an event as soon as one of its categories is deselected instead: in `remove_categories`, filter on `pl.any_horizontal` of the excluded columns.
- Stay connected overriding hand removals too: pass `all_arcs` instead of `remove_arcs(all_arcs, removed)` as the base in `graph.directly_follows_graph`.
- Other frequency in the nodes: `nodes.activity_frequencies` or the frontend `ActivityNode`.
- A new setting: field in `DfgRequest` (backend), `pnpm run build:modules`, a field in `DfgState`/`DEFAULT_STATE`/`toRequest` and a control in `DfgSettings.tsx`, a row in section 2 here and in the module note.
- Look: `SIZES`, `ELK_OPTIONS` and `COMPACT_OPTIONS` in `lib/dfgLayout.ts`; arc thickness `strokeWidth`, start/end grey `GREY`, dashes of connecting arcs and arrow size in `DfgGraph.tsx`.

## 6. Alternatives considered
- **Ocelescope's `Graph` visualisation** (`<Visualization>` of `@ocelescope/resources`): same layout engine, but no circles on nodes, fixed node width (cut names) and no room for later interaction. Own React Flow rendering instead.
- **Activity deselection without projection** (rounds 1–4: removing the node and its arcs, no arc between its neighbours): replaced by the projection, as in Ocelescope (Nina, 2026-11-15).
- **Arc threshold on arcs between activities only, start and end arcs always kept, no ties** (rounds 2–5): replaced by Ocelescope's ranking (Nina, 2026-11-15).
- **Automatic variant threshold per type** (round 4: the top 3 of each type in full): replaced by one default value for all types (Nina, 2026-11-15).
- **Computed default variant threshold** (round 6/7: the smallest whole percentage keeping the top 3 variants of every selected type, `default_variant_threshold`; 41 % in the running example): replaced by a fixed 80 % (Nina, 2026-11-16).
- **Arcs (display) only per type** (rounds 6/7): one limit for all types together is now the default, per type stays selectable (Nina, 2026-11-16).
- **Default variant threshold = share of the top 3, rounded up** (e.g. 60 % for 5 equally frequent coils): keeps the same variants here, but forces 100 % whenever a type has at most 3 variants, although these need much less; the smallest threshold that keeps the top 3 avoids this.
- **Path filter keeping ties**: degenerates when every object has its own variant.
- **Start nodes in the first layer** (as in the current Ocelescope viewer): what Nina disliked.
